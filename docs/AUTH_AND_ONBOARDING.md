# RFC 002 — Passwordless Google sign-in and first-workspace onboarding

**Status:** Proposed / Not implemented
**Decision owner:** AcademyOS
**Priority:** P0
**Last reviewed:** 2026-11-22
**Companion:** \`docs/ARCHITECTURE.md\`, \`docs/ROADMAP.md\`, GitHub Issue #1

## Product objective

One person can log in without typing a password, then own one or more branded workspaces. A teacher can own a SOLO workspace and also teach at an ACADEMY workspace. Each workspace can include different subjects and multiple teachers.

Do **not** build one independent set of credentials per academy. Reuse a single authenticated identity and enforce tenant authorization on every operation.

## Technical recommendation

1. Self-hosted **Better Auth** on the NestJS API; the core framework is free/open source. Hosting, PostgreSQL, email provider (if used) and any advanced managed services can still cost money.
2. **Google OAuth** as the primary login option (OpenID profile/email only). Offer a fallback email one-time code or magic link in a later iteration for people without Google; this requires sending transactional email.
3. Use the Better Auth **Prisma 7 adapter** with the existing Postgres database. Align the auth schema generated by the official Better Auth CLI with the existing \`User\` model, or model a distinct auth identity connected by a foreign key to the domain user. Do **not** simply enable the adapter against the current incomplete \`User\` schema; it lacks Better Auth session/account/verification requirements.
4. NestJS official documentation points to community-maintained \`@thallesp/nestjs-better-auth\`. Evaluate its tested version before adoption; inspect its body parser behavior and auth route mounting in our NestJS 12 setup.
5. Vue frontend uses \`better-auth/client\` to initiate \`signIn.social({ provider: 'google' })\` and restore its session. Protect routes in the backend, never merely through a client-side guard.
6. Retain the AcademyOS \`Workspace\` / \`WorkspaceMember\` model as our domain permission source of truth, at least in MVP. Better Auth's Organization plugin is a future alternative but must not duplicate our tenant membership table or mix students with auth admins.

## Costs and Google permissions

- Better Auth core: $0 license. Managed Better Auth infrastructure is optional.
- Basic Google login uses Google OAuth/OpenID identity scopes (openid/email/profile). Set up a Google Cloud OAuth client and its approved redirect URIs; no paid auth SaaS required.
- For public launch Google brand verification/policies may apply. Request Calendar or Drive permissions only **when the user explicitly connects those services**, not at sign-in; some extended scopes require separate sensitive/restricted-scope verification.
- OAuth dev callback (planned, verify actual Nest integration): \`http://localhost:3001/api/auth/callback/google\`; API routes for the product remain at \`/api/v1/\`. Production callback uses the verified production API origin. Avoid assuming that Nest's globalPrefix affects middleware routes.
- Never commit real GOOGLE_CLIENT_SECRET, BETTER_AUTH_SECRET or session cookies. The auth secret should have >=32 bytes of strong entropy.

## Experience A — Self-service SaaS teacher

Entry: \`/login\` (single primary CTA **Continue with Google**) → Google identity verified → determine memberships.

- Existing workspace member: enter the last selected allowed workspace, or show a compact selector if more than one.
- No workspace yet: show \`/setup\` wizard.
- Step 1 — **What are you creating?** [I'm an independent teacher] [I'm creating an academy]. No address, password or student information.
- Step 2 — **What is your space called?** Suggest \`{Google first name}'s Academy\`, allow editing display name, slug generated with availability check. Brand color optional.
- Step 3 — **Ready to teach**. Optional first subject(s), modality (online/onsite/hybrid), default timezone from the browser. Button **Create my space**. If the user skips optional items, create a valid workspace with no subject.
- Completion creates Workspace (SOLO/ACADEMY) and WorkspaceMember (OWNER) in **one server-side transaction**. Mark onboarding complete and navigate to a useful empty dashboard with a single suggested next action (add a class, invite a teacher, create a subject).
- Advanced setup (logo, pricing, Zoom/Meet/Drive, payments, policies) is progressive disclosure from Settings, not an onboarding blocker.

Estimated interactive inputs: workspace type + editable space name; optional subject/modalities. Google supplies the authenticated person's name/email/avatar. Never present a separate admin account/password creation form in this flow.

## Experience B — New isolated white-label deployment

Only if we deploy a **dedicated instance** for a school/teacher, rather than standard multi-tenant signup:

- Deployment has an installation status \`UNINITIALIZED\` and a one-use, short-lived, server-issued setup invite. The target identity/email is controlled by the operator/provisioning process.
- Setup entry \`/setup/activate?token=...\` requires valid token and Google sign-in with the **intended** identity. Tokens must be stored as hashes, expire, and be consumed atomically. Do not log or expose them in analytics/referrers.
- The backend checks installation status and token/identity; atomically creates the workspace and OWNER membership. Only then mark the installation \`ACTIVE\`.
- An anonymous visitor or unrelated Google account **must never become master/owner just because they arrived first**.
- Setup screen says \`Configure your academy\`; automatic admin identity creation from Google; optional name, branding and subject. Once activated redirect to the workspace dashboard; repeat activation must fail gracefully.
- Recovery from owner lockout is controlled separately by operator support or cryptographically verified owner recovery, with an audit trail.

Prefer **one multi-tenant AcademyOS instance** and one workspace per customer for MVP. Dedicated instances remain a deployment option, not the default.

## Identity vs roles (critical)

- Platform operator/superadmin (internal AcademyOS): separate privileged authorization not inherited from any customer owner.
- OWNER of workspace: manages academy branding, billing, roles, transfers and deletion within that workspace (additional confirmation for sensitive actions).
- ADMIN of workspace: manages teaching operations but cannot transfer ownership or access other workspaces.
- TEACHER: only assigned classes/courses and granted students.
- STUDENT: only their own enrolled classes and materials.
- GUARDIAN: consent/visibility according to verified relationship and age policies.

The browser cannot assign roles or set \`ownerId\` arbitrarily; authenticated server derives user ID and manages ownership in a transaction. Add an invariant that an active workspace cannot have zero owners without an explicitly secured transfer/deactivation workflow.

## Backend contract sketch (not implemented)

- Better Auth middleware: \`GET/POST /api/auth/*\` via official/community integration.
- \`GET /api/v1/me\` authenticated profile + accessible workspaces.
- \`GET /api/v1/workspaces\` lists **only** authorized memberships.
- \`POST /api/v1/workspaces\` creates new workspace and OWNER membership atomically. Validated type, name, slug; authenticated only, idempotency key, signup rate limits.
- \`POST /api/v1/tenant-activation\` consumes a dedicated deployment invite with matching Google identity; no open first-user-admin route.
- \`GET /api/v1/setup-status\` public safe boolean and no sensitive details.
- \`PATCH /api/v1/workspaces/:workspaceId/setup\` updates optional branding/subjects only after checking OWNER/ADMIN permissions.

Decide and test cookie same-site/security attributes and origins; prefer same-site proxy in production, HTTPS secure cookies, CSRF-safe flows, CORS allowlist, short session lifetimes with managed revocation.

## Acceptance tests (P0)

- Google success, cancellation, session expiry, and backend unauthenticated 401.
- New account completes wizard with 2 required choices; optional values can be skipped.
- Existing user re-enters without duplicate workspaces or onboarding.
- First signup and double-click/retry create only one initial workspace (idempotency).
- Owner of A can be Teacher in B and cannot read or update any A resource via B's scope.
- User cannot self-assign OWNER by manipulating a POST body or workspace ID.
- Dedicated deployment activation with expired token, wrong Google email, replay or concurrency is rejected.
- A disabled/banned user or revoked owner membership cannot access tenant resources.
- Google login alone does not grant Drive/Calendar scopes.
- UI meets accessibility keyboard, loading/error and narrow-screen tests.

## Implementation slices

1. Create and lock auth schema/migration with Prisma v7 and Better Auth, update generated client; wire Google environment without committing secrets.
2. Integrate auth middleware and API session guard; add Vue login/logout and return-path handling.
3. Implement workspace creation transactions, membership invariants, user-to-tenant resolution and RBAC tests.
4. Implement 3-step Vue onboarding with skeleton/empty states, progress persistence server-side and retry safety.
5. Implement optional dedicated activation route and tokens only if a real dedicated deployment is needed.
